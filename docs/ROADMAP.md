# Folio 发展路线图

> 最后更新：2026-09-23
> 本文是方向性规划。每一项落地前，会另出详细的技术方案（见 `docs/superpowers/specs/`）。

---

## 一、现状

### 规模

| 指标 | 数值 |
|---|---|
| 主文件 | `index.html` — 5054 行 / 239KB（单文件，全部逻辑与样式） |
| 本地依赖 | ~2.9MB JS + 1.5MB KaTeX 字体（大库已懒加载） |
| 功能视图 | 9 个：编辑器 / 压缩工具 / 图片工具 / PDF 工具 / 文档修复 / 知识库 / 单词库 / 思维导图 / 专注 |
| 持久化 | 12 个 `folio.*` localStorage 键 |
| 仓库 | 8.7MB（含 .git 2.9MB） |
| 分发 | 双击打开 / GitHub Pages / PWA |

### 战略资产（已经做对的事，不要破坏）

1. **零摩擦** —— 双击就能用，不安装、不登录、不联网。同类工具（Notion / Obsidian / 语雀）都做不到。
2. **隐私是结构性的** —— 数据从不离开本机。这不是政策承诺，是架构事实。
3. **离线完整** —— 所有第三方库已本地化，无 CDN 也能跑（国内网络环境下尤其重要）。
4. **审美不模板化** —— 杂志/暖纸风格，一眼不像"AI 生成的东西"。
5. **能力广度** —— "文档编辑 + 文件工具"在同一处，这个组合本身就少见。

## 二、核心瓶颈：localStorage 的 5MB 墙

**这是当前最大的结构性约束，也是后续一切的前提。**

localStorage 的配额约 5MB（字符）。而应用把**完整 HTML** 存进多个键：

| 键 | 内容 | 单份体积 |
|---|---|---|
| `folio.docs` | 所有打开的标签 | 全部文档 HTML |
| `folio.draft` | 当前草稿 | 1 份完整 HTML |
| `folio.snapshots` | 版本快照 | N 份完整 HTML |
| `folio.history` | 历史记录 | N 份完整 HTML |
| `folio.library` | 知识库 | 每篇完整 HTML |

### 实测（按真实文档结构生成 markdown 测算）

| markdown | 渲染后 HTML | 仅快照（30 份） | 结果 |
|---|---|---|---|
| 50KB | 110KB | 3.2MB | 逼近上限 |
| **100KB** | 220KB | **6.4MB** | **超配额** |
| 200KB | 440KB | 12.9MB | 严重超配额 |

**后果**：超出配额时 `setItem` 抛 `QuotaExceededError`。此前这些写入**没有 try/catch**，抛错会跳过后续步骤（尤其 `saveDocsState`），导致标签状态与内容不一致——表现为"刷新后内容错乱、丢失"。

> 该问题已于 2026-09-23 做过一轮止血（统一 `safeSet` + 按总量预算保留完整版本 + 全部写入点加固），详见提交 `d5d9bf6`。**但那是止血，不是治本**：5MB 的墙还在，只是不再摔得那么惨。

**结论**：只要还困在 localStorage，"积累型工具"（知识库、快照、历史、长期的记录）就永远走不远。**必须迁移到 IndexedDB。**

## 三、三条发展路线

### 路线 A：个人知识工作台（深化自用）★ 推荐

把 Folio 做成"真正能长期用、能积累"的本地知识工作台。

- **迁移 IndexedDB** —— 拆掉唯一的硬墙
- 顺带解锁：全文检索、无限快照、大文档、知识库无上限
- 可选：接入 **File System Access API**，能真正写进指定文件夹 → 从"下载式"变成"真正的本地笔记应用"
- 补上**心情记录**（设计已完成，见 `docs/superpowers/specs/2026-08-30-mood-log-design.md`）

### 路线 B：打磨成形（作品 / 产品向）

- 拆模块 + 构建步骤，但**仍产出单文件** —— 兼顾可维护性与零摩擦分发
- **建立回归测试**（见 ④）
- PWA 安装体验、多语言

### 路线 C：扩展能力边界

- 导出格式扩展（EPUB、微信公众号等）
- **PDF 排版能力升级**（见 ②，最高优先级）
- **公文 / 报告模板**（见 ③，差异化最强）

## 四、优先级路线图

排序依据：**杠杆 × 真实使用频率 × 风险可控度**。

### ① IndexedDB 迁移 ★ 最高杠杆

**目标**：把 `folio.*` 的持久化从 localStorage 迁到 IndexedDB，配额从 5MB → 数百 MB 起。

**为什么**：它是其余一切的前提。不拆这堵墙，知识库/快照/记录类功能都只能小打小闹。

**要点**
- 统一封装一个存储层（`idb.get/set`），替换现有的 `get*/set*` 系列，业务代码尽量不动
- **平滑迁移**：首次启动时检测 localStorage 是否有旧数据 → 搬进 IndexedDB → 校验成功后再清理（不能先删）
- 申请**持久化存储**（`navigator.storage.persist()`），避免浏览器在磁盘紧张时回收
- 保留 localStorage 作为降级路径（隐私模式 / 老浏览器）

**风险**：中。迁移逻辑涉及用户数据，**必须先备份后迁移、且可回滚**；需要充分测试"迁移中断"的情形。

**验证**：导入一篇 500KB 的 markdown，确认快照/历史/知识库都不再触发配额错误。

---

### ② PDF 导出升级 ★ 使用频率最高

**目标**：让"导出 PDF"从"浏览器打印"升级为真正可控的排版输出。

**为什么**：PDF 是**使用最多的导出方式**；而当前路径的天花板很低。

**现状的不足**
- 无页码、无页眉页脚
- 分页不可控：代码块/表格/图片会被拦腰截断，标题可能与正文分离（孤行）
- 排版参数（纸张、边距、字号、行距）不可配
- 输出质量依赖浏览器打印引擎

**两条技术路径**

| | A. 强化打印路径（`@media print`） | B. pdf-lib 自研排版 |
|---|---|---|
| 做法 | 精细化分页 CSS | 自己测量文字、分页、绘制 |
| 能拿到 | 分页质量大幅改善 | 页码/页眉/目录/完全可控 |
| 拿不到 | **页码、页眉页脚、目录** | —— |
| 工作量 | **小** | 大 |
| 风险 | 低 | 中高 |
| 代价 | —— | 需嵌入中文字体（CJK 字体 5–15MB，需子集化）＋ fontkit 依赖 |

**建议：分阶段**
1. **先做 A**（低风险、立刻见效）— ✅ **已完成 2026-09-23**
   - `break-inside: avoid`：表格行、图片、引用块、行内公式不跨页断裂
   - `break-after: avoid-page`：标题不与其后正文分离
   - `orphans` / `widows`：避免单行孤行
   - 导出前面板可选：纸张（A4 / A3 / Letter）、边距、正文字号（五号 / 小四 / 四号）、行距；选择本地记忆，预览实时反映
   - 验证方式：无头 Chrome 真实驱动 UI 导出，确认实际输出页面尺寸随选择变化（A4 / A3 / Letter 均一致），并回归确认界面元素无泄漏
2. **再评估 B**：只有当"页码 / 目录"成为**必须**时才投入。页码有一个廉价替代——引导用户在浏览器打印对话框勾选"页眉和页脚"（Chrome 会带上页码）。

**验证**：拿一篇含代码块、表格、图片、长段落的多页文档，逐页检查分页质量。

---

### ③ 公文 / 报告排版模板 ★ 差异化最强

**目标**：一键套用规范的中文公文/报告格式。

**为什么**：应用中已装 **方正小标宋简体 + 仿宋_GB2312**（中国公文标准字体），说明真实用途包含公文/报告写作。而 Typora / Obsidian / 通用工具在这件事上都不好用——**而本应用有字体、有编辑器、有导出链路，闭环已经齐了**。

**要点**
- 预置格式方案：标题（方正小标宋二号）、正文（仿宋_GB2312 三号）、行距（固定值 28 磅）、页边距、层级序号
- 一键套用 + 导出 Word/PDF 时保持格式
- 可存多个模板（通知 / 报告 / 论文）

**风险**：低（纯前端规则 + 样式）。

**验证**：套用后导出的 Word/PDF 在 Word 中打开，格式与公文规范一致。

---

### ④ 回归测试集 ★ 性价比最高的工程投资

**目标**：把反复出现的回归挡在提交之前。

**为什么**：已经多次被同类回归咬到——分屏丢内容、打印截入界面、导航点击失效、长文档错乱。而这些**都是可以自动拦住的**。实测证明：验证打印问题时临时搭的"无头 Chrome 真实打印 + 文本比对"只花了十几分钟，就能给出 A/B 结论。

**要点**
- 用无头 Chrome 跑关键路径：
  - 打印输出中**不含任何界面元素**（本次已验证过的方法，直接固化）
  - 长文档：粘贴大文档后各存储键不超限、标签与内容一致
  - 导航：点击定位、滚动跟随高亮
  - 分屏：进入/退出/互换后内容不丢
- 提交前的检查清单

**风险**：低。**收益**：防止已修好的问题复发。

---

### ⑤ 心情记录 ★ 低成本，补上"人"的一面

设计已完成：`docs/superpowers/specs/2026-08-30-mood-log-design.md`（日历回望 + 悬浮记录 + 情绪趋势）。

定位：Folio 作为"工作/学习工具"偏硬，心情记录补上情绪与长期积累的一面，也正好是"积累型工具"的第一个受益者——**建议放在 IndexedDB 迁移之后做**，这样它一开始就没有 5MB 的心理负担。

## 五、明确不做（避免走偏）

| 不做 | 原因 |
|---|---|
| ❌ 云账号 / 在线协作 | 会毁掉"零摩擦"和"隐私"这两张王牌 |
| ❌ 重写为移动 App | 投入巨大；现有"网页 + 可装桌面"已是轻路径 |
| ❌ 无边界堆功能 | 9 个视图已不少，**深度比广度值钱**——把 PDF 做透，好过再加 3 个格式工具 |
| ❌ 引入 CDN / 在线依赖 | 离线可用是核心资产 |

---

## 六、建议推进顺序

```
① IndexedDB 迁移        ← 拆墙，其余一切的前提
② PDF 导出升级（先做 A 阶段）  ← 使用频率最高，风险低、见效快
③ 公文 / 报告模板        ← 差异化，贴合真实用途
④ 回归测试集            ← 防止已修问题复发
⑤ 心情记录              ← 设计已就绪，成本低
```

**下一步建议**：从 **② 的 A 阶段（打印分页精细化）** 动手——它是每天都要用的收益，改动比 ① 收敛得多、风险低、可立刻验证。① 紧随其后，因为它是所有"积累型"功能的地基。
